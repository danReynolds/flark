# RFC 031 — Code colors outside the input callback

Status: implemented in the Flutter workbench for qualification. Automated host
checks and the first hands-on browser exploration pass. Sustained color-transition
capture and the full frame/device gates remain open. See the
[browser review](../../../packages/flark_tree_sitter/BROWSER_DOGFOOD_REVIEW.md).
Named consumer: Flark V5 code-fence editing in Flutter native/web and Fleury.

## Decision proposed

Keep Markdown recognition, source edits, indentation, caret legality and history
in the synchronous V5 transaction. Run optional Tree-sitter syntax coloring in
an owned worker. A color result must match the complete current code-body source
and selected language. While it is pending, render the current text with the
plain code style. Colors may not affect font metrics, selection, layout, Markdown
interpretation, indentation decisions or whether markers are hidden.

This is a narrowly specified addition to RFC 030, whose appendix excludes an
asynchronous live-rendered tier. It does not enable such a tier for Markdown or
increase the document envelope. It explicitly relaxes immediate code coloring;
the synchronous structural representation remains the only representation.

## Why

The original complete-snippet service cost for an approximately 8K Dart editing
journey was 23.9 ms median in dart2js/Node. Supported incremental context parsing,
upstream highlighter reuse, and a compact range protocol roughly halved it.
That remains too much work before Flark's transaction, layout and paint.
The released upstream highlighter reparses its input and does not accept an
existing tree. A private fork or a new highlighting interpreter would add a
language-engine maintenance obligation to a Markdown snippet feature.

The prototype uses the same Rust engine in a Dart isolate on native and a Web
Worker on web. Its additional JavaScript is transport code, with no grammar or
indentation rules. The main thread decodes and validates compact returned ranges.
The [performance review](../../../packages/flark_tree_sitter/PERFORMANCE_REVIEW.md)
contains the measurements and limitations.

## Ownership and failure

`CodeAnalyzer.proposeEdit` remains synchronous. The optional
`CodeHighlightWorker` owns a worker and serves one active snippet stream. There
is one running request and at most one pending replacement. New input completes
superseded requests with null. Disposing completes outstanding requests with null
and terminates the worker. Transport failure reports an error; the host keeps
the current plain code text and may explicitly create a new worker.

The host must also compare returned source and language against the current
projection's requested fences before adoption. A result already completed before
a new request cannot be revoked. Deleting a fence, changing language, entering
source mode and switching documents invalidate pending adoption. Exact immutable
snippet results may be cached across undo or identical fences: their ranges are
relative to code text, never absolute Markdown positions. A container change
therefore uses the current projection's source mapping and geometry. No source
edit, caret or undo entry is ever generated by a color response.

Do not create one worker per painted code row. Host integration must own and
dispose the worker at editor lifetime, prioritize the active snippet, and define
bounded caching/scheduling for other visible fences. The prototype's latest-only
queue is not a general multi-document background queue.

## Review and adoption gates

1. Compare the component implementation against fresh parsing and synchronous
   coloring, including incomplete syntax, Unicode, CRLF and language changes.
2. Measure input callback cost separately from color latency in native AOT and
   both Dart browser runtimes, with rapid edits, Enter and automatic outdent.
3. Verify real Flutter source/caret/selection/undo and next-character behavior in
   top-level, quoted and list-contained fences. Assert the first frame, then the
   later color-only frame. Delayed results cannot affect geometry or source.
4. Dogfood repeated typing, selection and IME with deliberately delayed workers.
   Whole-fence color flicker, starvation across visible fences, cold grammar
   pauses, worker memory and CSP/asset distribution are explicit checks.
5. Re-measure the full frame and difficult admitted snippet shapes. Warm component
   medians are not a p99 end-to-end or physical-device qualification.

The worker direction is rejected if its plain-to-colored transition is distracting
or its lifecycle/scheduling burden grows into a second editor. At that point,
compare a deliberately smaller synchronous highlighting contract against a
supported upstream API change. Do not restore stale colors, fork private
highlighter internals, or silently lower the 8,192-unit admission limit.
