# Composer playgrounds and Fleury parity — 2026-09-20

The existing Flutter and Fleury playgrounds are now the composer examples.
They open with a large bounded document surface, formatting controls, New
document and Copy Markdown. Theme customization is optional, beside the
surface on wide windows and above it on narrow ones. There is still one live
editor. Draft changes remain session-local; New document is undoable.

## Implementation

- Fleury paints thematic breaks with `FlarkCellTheme.thematicBreak`, respecting
  container gutters, theme colors, source mode and selection. The kernel's
  source/projection contract is unchanged.
- `FlarkEditorView(showToolbar: true)` supplies paragraph/H1–H6, bold, italic,
  strikethrough, inline code, link/image forms, Undo/Redo and source mode. The
  option defaults off for existing embedded surfaces; the example enables it.
  Read-only views omit authoring controls. Narrow theme customization temporarily
  hides this bar to keep the document usable, without remounting its surface.
- Fleury's active-fence picker uses the same Tree-sitter language catalog as
  Flutter: Automatic, Plain text and 14 language choices. Choice is persisted by
  `SetCodeLanguage`; highlighting and indentation continue using the same engine.
  Moving selection or changing the document invalidates an open picker.
- Flutter's existing toolbar gains paragraph/H1–H6, strikethrough and inline code.
  Inline controls are disabled inside code fences and in source mode. Menu targets
  are captured when opened, so later rebuilds cannot redirect a stale choice.
- `SetHeadingLevel` accepts a collapsed caret on a blank row, allowing a new
  document to choose a heading before typing. Existing paragraph, container,
  code and source-mode handling remains in the shared kernel.
- No separate formatting state or document model was added to either example.
  Controls use shared kernel formatting state and command/history APIs.
  Playground theme settings continue to style the renderer separately.

## Formatting-state follow-up

Dogfooding exposed that Flutter's default selected icon color was too subtle,
and that a caret-only state could misrepresent a mixed selection. The shared
[formatting API](formatting_controls.md) now supplies on/off/mixed state and
edit availability, with idempotent `SetStyle` and controller convenience methods.
Both toolbars consume it. Flutter adds a selected fill and a distinct mixed
indicator; Fleury retains inverse selected buttons and adds a mixed indicator.
Selection formatting preserves other inline styles and is admitted atomically.

The updated local suites pass: kernel 816, Flutter host 821, Fleury host 107.
These include listeners, pending input, mixed forward/reverse selections,
explicit on/off idempotence, Undo/Redo, keyboard and caret-driven toolbar state,
and source/code/unsupported-range restrictions. Partial-span and cross-block
formatting transformations remain outside the bounded range contract.

Both browser candidates were rebuilt and dogfooded with pending Bold, typed
bold/plain text, Select All, mixed state and normalization. Flutter's mixed
state initially merged into the toolbar's accessibility container; a
`MergeSemantics` boundary now attaches it to the individual button, verified
in the browser and in a widget semantics assertion. Fleury also provides an
accessible state description because its browser presenter exports a generic
button value only as metadata. The example suites still pass (38 Flutter,
6 Fleury). These previews use separate revision URLs to preserve open drafts.

## Review and validation

Local review caught and corrected two issues before handoff:

1. Fleury's toolbar removal changed unkeyed child reconciliation and recreated
   a surface with an already-attached bounds observer. The editing surface now
   has stable keyed identity across toolbar/read-only changes. A mounted test
   covers that transition; the narrow playground suite exercises theme toggling.
2. Flutter's dropdown callback can be replaced during a rebuild while its menu
   stays open. Capturing the target during build was insufficient. Both language
   and heading menus now capture it on open; tests move the selection before
   choosing and verify no mutation.

Passing local checks:

- Shared kernel: 788 tests, including blank-row headings H1–H6, caret and Undo.
- Flutter host: 819 tests, including selection formatting, heading choices,
  stale menus and source/code restrictions at 360px and 1100px widths.
- Fleury host: 105 tests, including rule painting within quotes at 24/100 cells,
  source preservation, language selection/Undo, continued input and read-only.
- Flutter example: 38 tests. Fleury example: 6 tests, including 40×24 and
  100×32 cell layouts and existing theme/color/export journeys.
- Both browser builds completed. Fleury browser dogfooding checked language
  selection through keyboard controls, source tags, Undo, visible rules, a new
  heading before typing, bold entry and the optional theme panel. Flutter Wasm
  dogfooding checked New document, heading selection, continued typing and the
  panel at normal and 460×780 browser sizes.

This is local review/testing, not independent approval or CI. CI was skipped
at the owner's request. Native input/lifecycle/VoiceOver/device qualification,
table structure controls and dedicated footnote UX are explicitly deferred.
The playground improvements do not close those release or feature boundaries.
